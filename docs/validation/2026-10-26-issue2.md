## 结果

- Attempt 2 的 `/v1/video/generations` 请求使用同两张本地测试 PNG、保存历史，并通过捕获的现代聊天流程执行。初始请求包含两张 `type=1` 图片附件和视频 `chat_ability`；只有一次权威澄清后的纯文本确认续轮，使用链中 `index_in_conv=4`，视频续轮未发送 `conversation_init_ext`。
- Attempt 2 返回 HTTP 200 和一个视频结果。只读链确认同一会话的 `2074` 结果块包含 `type=2`、`status=3` 及有效 HTTP(S) 地址。Range 读取返回 HTTP 206、`video/mp4`，样本包含 MP4 `ftyp`；浏览器播放到 `readyState=4`，实际媒体尺寸为 720×720，时长 15.072 秒，播放时间推进。
- 链中视频元数据报告 384×384、15.073 秒；实际解码的 MP4 为 720×720、15.072 秒。代码使用链返回的视频地址字段；签名地址未保存或发布。尺寸差异尚未解释。
- 上游助手在确认后的消息中表示参考图片资源不可用，并称会直接按文字描述生成视频。虽然 API 确实返回了可播放视频，但无法证明这段视频使用了两张参考图，因此**不算图生视频验收通过**。助手回报 15 秒，最终媒体也是约 15.07 秒，尽管请求默认参数为 10 秒；本项目不承诺上游一定遵守请求时长。

基于已保存的请求对照，原生附件的 `image_ori.url` 为空，而 Attempt 2 的 API 附件将 `upload_image` 返回的 CDN 地址填入该字段。已加入一个 video-only 调整：视频附件保留原始 `uri`、尺寸、格式和文件名，但将 `image_ori.url` 留空以匹配原生结构；普通聊天仍填入 CDN 地址。Attempt 3 的真实 API 请求已验证此出站结构，并确认两个附件 URI 都匹配本进程刚上传的资源，但没有 `2074` 成片结果；因此该字段调整是否能修复参考图绑定仍未验证。

## 附件与上传路径

Attempt 3 的 API 初始请求包含两张 640×640 PNG 图片附件，`image_ori.format` 为 `png`，`image_ori.url` 为空；出站的两个 URI 均与本进程上传返回的 URI 匹配。此前保存的原生网页请求也包含两个同尺寸、同格式的图片附件，且 `image_ori.url` 为空。URI 与 URL 值均未输出，无法比较 URI 前缀、域名或长度。

代码中的 `upload_image` 通过 `/samantha/pages/upload_image` 上传，再通过 `/alice/message/get_file_url` 获取图片地址。当前 native/API 抓包均未记录图片上传请求路径，所以没有证据确认原生页面使用的上传管线。Attempt 3 在调用生成器前只读 GET 两个新上传 CDN 地址；二者均返回 HTTP 200、`image/png`，解码为 640×640，metadata 尺寸与格式一致，下载 bytes 和像素均与本地源 PNG 匹配。这证明本次 CDN 内容可读且与输入源一致，但不证明上游视频工具通过 TOS URI 绑定了参考图。

Attempt 3 结束后进行的一次无生成上传诊断使用 `BrowserClient(headless=False)` 新开空白聊天页。BrowserClient 报告选择 Chrome 候选、`headless=false`、页面为 HTTPS 豆包域名，唯一标题标记已设置，生成请求拦截器在导航前启用；未提交 API 或打开历史。Computer Use inventory 看到一个豆包标题的 Chrome 窗口，但没有看到标题标记；读取该窗口时工具拒绝继续，理由是无法以足够置信度确定当前浏览器 URL。没有上传测试图片，也没有使用其他自动化方式绕过。随后用 `quit` 正常关闭了我启动的诊断进程，9090 无监听；Playwright 未提供实际可执行文件 basename。
